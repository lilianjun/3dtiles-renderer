# ADR-0011: 3D Tiles 1.1 support — bare glb content and implicit tiling (P10)

Date: 2026-09-29
Status: accepted

## Context

P5–P9 gave real, pixel-verified support to every 3D Tiles 1.0 tile
format (b3dm / i3dm / pnts / cmpt). Modern tilesets, however, are
increasingly 3D Tiles 1.1: tile content can be a bare `.glb` with no
b3dm wrapper (`3DTILES_content_gltf`), and tile hierarchies can be
implicit (`3DTILES_implicit_tiling` — QUADTREE/OCTREE with subtree
files). cesium-native v0.64.0 claims 1.1 support, but neither path had
been verified through our SDK chain.

## Investigation

We read cesium-native v0.64.0 sources (not memory) before writing any
fixture:

- **Bare glb content**: `registerAllTileContentTypes()` registers magic
  `"glTF"` → `BinaryToGltfConverter::convert`, which parses the glb
  with `GltfReader` and moves `GltfReaderResult.model` into the
  `GltfConverterResult`. The `TilesetJsonLoader` continuation
  (`TilesetJsonLoader.cpp` ~L1296) is format-agnostic — it only checks
  `result.errors` and forwards `*result.model` — so bare glb flows into
  the **same** SDK `prepareInLoadThread` → render bridge as every 1.0
  format. `TilesetJsonLoader` does not gate on `asset.version`, so a
  `"1.1"` tileset needs no special handling. (P5's 1.0 fixture already
  rendered bare glbs as `root.glb`/`child_b.glb`; P10 makes the 1.1
  declaration explicit with `extensionsUsed: ["3DTILES_content_gltf"]`.)
- **Implicit tiling**: a root tile carrying the
  `3DTILES_implicit_tiling` extension triggers
  `createImplicitQuadtreeLoader()` (required fields:
  `subdivisionScheme`, `subtreeLevels`, `availableLevels` — or legacy
  `maximumLevel` — and `subtrees.uri`). Subtree files are fetched
  through the regular `IAssetAccessor` and parsed by
  `SubtreeFileReader`; a subtree **not** starting with the `"subt"`
  magic is parsed as plain JSON, so the fixture subtree is hand-written
  JSON with `constant` availability — no bitstream buffers needed.
  Content/subtree URL templates use `{level}`/`{x}`/`{y}` placeholders
  resolved against the tileset.json base URL
  (`ImplicitTilingUtilities::resolveUrl`).

The decisive experiment: two self-generated deterministic fixtures
(`tests/data/gen_p10_11_tileset.py`, no network) rendered through the
**existing** SDK path with **zero code changes**:

- `p10_11_glb/` (`asset.version: "1.1"`, bare-glb root + child):
  2 tiles rendered, 4915 orange + 2293 teal pixels.
- `p10_11_implicit/` (QUADTREE, subtreeLevels/availableLevels 2, JSON
  subtree with constant availability, 5 per-tile glbs): **5 tiles
  rendered** — the subtree → tile-URL-template → per-tile glb chain
  works end to end. Pixel counts: red 383 (L0), green 1624, blue 2811,
  yellow 297, magenta 548.

A pixel-counting lesson: box top faces render *near* but not exactly
the base sRGB color (blue tops read `(4,4,194)`), so `tiles11_test.py`
uses tolerant range masks rather than the exact matching that worked
for P8's unlit pnts points.

## Decision

3D Tiles 1.1 support needs **no SDK code change**: the existing generic
converted-model path already covers bare-glb content, and implicit
tiling is entirely inside cesium-native (subtree fetch → tile URL
templates → per-tile conversion).

## Consequences

- New test coverage: `tests/data/gen_p10_11_tileset.py`
  (deterministic, no network), `tests/tiles11_test.py`
  (`tiles11_screenshot`: 2-tile bare-glb assertions + 5-tile implicit
  assertions), fault-injection cases M/N/O (corrupt bare glb, missing
  subtree file, illegal `subdivisionScheme` — all graceful skips), and
  `sanitizer_11` in the linux-asan gate.
- Honest boundaries:
  - Only QUADTREE implicit tiling is pixel-verified; OCTREE uses the
    same loader family but was not exercised.
  - Only `constant` subtree availability is tested; bitstream
    availability buffers were not exercised (cesium-native parses them,
    our fixture just doesn't need them).
  - `3DTILES_bounding_volume_S2` and other 1.1 extensions were not
    tested.
  - Tile `transform` rebase (P5) was proven on 1.0 paths sharing the
    same render bridge; not re-proven for 1.1 content specifically.
  - Android/Windows/iOS still have no on-device verification.
